## 바인드 변수를 쓰면 조회가 느리던 것

Toad 에서 0.06초에 나오는 조회가 바인드 변수를 쓰면 1분 30초 걸리고, 값을 직접 쓰면 바로 나오던 것.

- 원인: 문자열 바인드를 NVARCHAR2 로 보냈다. VARCHAR2 컬럼과 비교하면 Oracle 이 **컬럼 쪽을 바꿔**(`SYS_OP_C2C(컬럼) = :바인드`) 그 컬럼의 인덱스를 쓰지 못하고 테이블 전체를 읽는다.
- 이제 Toad·SQL*Plus 처럼 **VARCHAR2 로 보낸다** — 실행(Ctrl+Enter·F5 의 바인드), PL/SQL 호출(디버거 등), 여러 행 넣기(가져오기·데이터 복사). 4000바이트를 넘는 값은 전과 같다.
- 실제 Oracle 에서 바인드로 조회했을 때 실행계획이 인덱스를 쓰고 `SYS_OP_C2C` 가 없는지 보는 통합 테스트를 넣었다.

## 분석 결과 — 여는 것·지우는 것이 빨라졌다

큰 분석 결과(단위 수천 개)에서 결과를 여는 데 오래 걸리고, 그동안 창이 멈추던 것. 단위 3,000개로 잰 값:

| | 전 | 후 |
|---|---|---|
| 결과 목록 | 1.0초 | 0.08초 |
| 단위 목록 | 1.5초 | 0.09초 (분석·가져오기 직후 처음 한 번만 2초) |
| 화면으로 보내는 통합 결과 | 173MB | 44MB |
| 가져온 결과 지우기 | 3.8초 | 0.02초 |

- **창이 멈추지 않는다** — 결과 목록·단위 목록·통합 결과 읽기·지우기를 작업 스레드에서 한다 (전에는 앱의 메인 스레드에서 돌아 그동안 창이 멈췄다).
- 결과 목록: 통합 결과 파일(수백 MB)을 통째로 읽던 것을, 만든 시각만 파일 맨 앞에서 읽는다.
- 단위 목록: 단위 요약 색인(`integrated/units-index.json`)을 두고, 단위가 바뀌지 않았으면 그것만 읽는다 (단위를 분석·합치면 알아서 다시 만든다).
- 통합 결과: 테이블마다의 '영향 받는 시작점' 은 개수와 앞의 50개만 화면으로 보낸다 (툴팁에 "… 외 N개"). 파일의 원본은 그대로라 MCP·CLI 는 전체를 본다.
- 지우기: 폴더 이름만 바로 바꾸고 실제로 지우는 것은 뒤에서 한다. 지우다 만 것은 다음에 분석 화면을 열 때 마저 지운다.
